# M1 slice 5: proving native/web locator compatibility (resolves handoff F1 for the formats below)

Run 2026-11-17. Question (contracts/t005/README.md, ADR-0027): does a locator produced by the preserved Android reader mean the same
thing to the pinned web reader on the same file and version, including after layout and font changes? Ancestry or syntax is not evidence;
renderer behaviour is. All fixtures are synthetic and generated by `scripts/t007/locators/make_fixtures.py`.

## Method (all scripts under `scripts/t007/locators/`, MIT, none copies engine code)

| Script | What it does |
| --- | --- |
| `ast-compare.mjs` | Parses every Foliate file of both engines to a syntax tree (ignoring formatting) and reports semantic differences: `ast-compare.json`. |
| `run.mjs` | Serves the pinned web engine (`apps/web/public/reader/vendor/foliate-js`) and the preserved Android engine (`apps/android/.../assets/reader/foliate`) to two Chromium pages and cross-resolves locators: `results.json`. |
| `device-check.mjs` | Attaches over DevTools to the REAL Android reader WebView on the emulator (Chrome 154) and runs the same checks against the web engine on the same EPUB file: `device-results.json`, `device-stress/device-results.json`. |
| `pdf-check.mjs` | Ground truth for PDF page identity from PDF.js 6.5.438: `pdfjs-pages.json`. |
| `web-cfi.mjs`, `../second_client.py` | Produce a CFI with the web engine and save it as another device would, for the end-to-end resume check. |

Every position is reduced to an engine-independent fact: (spine index, UTF-16 text offset in the section body). Checks: E0 self-resolve
(validates the harness), E1/D1/D2 a locator from engine X resolves to the same text in engine Y at a different viewport and font size,
E2 navigating Y to X's locator shows that text on the page, E2b the locator Y reports is taken to a third layout in X, E3 range locators
resolve to the same text and offsets, E4 range CFI strings are byte-identical, E5 collapsed points resolve.

## Results

| Scope | Result |
| --- | --- |
| Desktop Chromium, stress EPUB (6 chapters: nested inline markup, links, `<br/>`, lists, tables, ruby, comments, emoji surrogate pairs, combining marks, RTL, image), both directions, 3 layouts | 36 page positions: E0 36/36, E1 36/36, E2 36/36, E2b 36/36; 84 range and 84 point locators: E3 84/84, **E4 84/84 (identical strings)**, E5 84/84. |
| Desktop Chromium, stress FB2 (sections, epigraph, poem, cite, subtitle, table, style, emoji, combining marks), both directions | 12 pages 12/12 on every check; 42 ranges: E3, E4 and E5 all 42/42. |
| **Device WebView**, simple EPUB | 41 web-produced positions resolve on the phone identically (41/41) and the phone shows them (41/41); 18 phone-produced positions (font changed to 28 px) resolve identically in web (18/18, 18/18); 96 ranges: same text and offsets 96/96, **CFI strings identical 96/96**, collapsed points 96/96. |
| **Device WebView**, stress EPUB | 36/36 and 36/36 (web to phone), 20/20 and 20/20 (phone to web, font 28 px), 72 ranges 72/72, strings identical 72/72, points 72/72. |
| End to end on the device (`e2e-sync/`) | With canonical sync on, paging in the phone's reader wrote a `foliate-cfi` position to the server (revision 6, device "Android"); a CFI produced by the web engine for "Synthetic Tale" at 60% (`epubcfi(/6/10!/4,/14/1:274,/18/1:136)`) saved from another device made the phone reader open on "Chapter 5" at 59% (`03-phone-resumed-at-web-position.png`). |

## What the source comparison adds

`ast-compare.json`: `fixed-layout`, `overlayer`, `progress`, `search` are semantically identical in both trees. `epubcfi.js` differs in one function,
`nodeToParts`, where the pinned engine skips filtered-out parent nodes; no caller in either tree passes a filter to `fromRange`/`toRange`, so that
branch never runs (checked by grep). `epub.js`, `fb2.js`, `view.js` (Android adds Kobo/KOReader helpers), `paginator.js`, `text-walker.js`,
`comic-book.js` and `mobi.js` (`MOBI6`) differ; the first two are covered by the behavioural results above for the cases tested, the rest are not
CFI generation or are out of scope.

## Policy that follows (code: `LocatorPolicy.NATIVE`, pinned by `NativePolicyTest`)

- **Allowed:** `foliate-cfi` and `foliate-range` selections for **EPUB and FB2**; `pdf-page` for **PDF at page granularity** (native reports `x=0, y=0`
  and never claims sub-page coordinates or rectangles, so crop/rotation conversion is not involved); `comic-page` for all comic formats.
- **Still device-only:** KEPUB, MOBI, AZW, AZW3 (no fixtures; the `MOBI6` converter differs between the engines), `pdf-rectangles` selections,
  everything not listed. Nothing was relabeled: a refused locator is neither sent nor applied.

## Limits (not covered, stated plainly)

- Synthetic fixtures only; no real-world EPUB/FB2 corpus (calibre output, publisher EPUBs, fixed-layout, vertical writing, SVG covers, footnote
  structures), no KEPUB or MOBI/AZW3, no right-to-left pagination checks beyond RTL text inside the stress book.
- The desktop comparison is Chromium (the device is Chromium-based WebView, Chrome 154); other browsers use their own DOM but not their own CFI code.
- PDF: page identity was verified for one 7-page edge-case file by search/visual, not exhaustively; real PDFs with broken page trees, JavaScript page
  reordering or very large documents are untested. Sub-page coordinates are unproven and unused.
- The web reader app itself (frame, bridge, saver) was not driven in a browser; the engine API both bridges use (`relocate` cfi, `goTo`) was.
- Compatibility was shown for these two engine copies at these revisions. A changed engine must re-run these scripts (profile rule).
