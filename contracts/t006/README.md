# T006 delivery and integration contract

Prepared 2026-11-16 under accepted ADR-0073 through ADR-0076. These files describe implementation obligations, not implemented routes or tested interoperability. `openapi.json` has 26 /api/v1 management operations; `protocols.openapi.json` has 16 root-mounted wire operations. `scenarios.json` contains 38 acceptance scenarios. `examples.json` has 23 schema-positive/negative cases; `digest-vectors.json` has nine reproducible binary-hash vectors. Run `python scripts/contracts/check_t006.py` for static preparation checks.

## Shared authority and mutation rules

Management APIs keep T003 bearer or browser cookie transport; unsafe browser requests require X-CSRF-Token and existing origin checks. Protocol credentials cannot call management APIs, log in to the web app or bypass library grants. Resource authority comes from the authenticated principal, never a body owner/user ID. Administrators do not gain private recipients, SMTP passwords, KOReader positions/candidates or delivery history. Admin-only settings do not reveal another user's data. Another user's private UUID returns 404. Unauthorized or ungranted protocol objects have no metadata/private candidate body; avoid a lookup response distinguishing another user's content. Disabled services return 503 with `integration_disabled`; revoked/disabled credentials use 401. Rate limits use 429.

Management writes use operation UUIDs. Versioned settings, recipients, bindings, cancellation and explicit resolution compare decimal-string `baseRevision`; new resources start at zero. State, receipts and jobs/history/candidates are atomic. Identical user+operation requests replay original status/body; changed semantic payload is 409 `operation_id_reused`. Receipt fingerprints include method, resource, normalized body and a safe deterministic digest of supplied secret fields, never plaintext secret material. Existing T003/T005 receipt uniqueness must not collide: use the authenticated user's existing cross-operation namespace or an explicit unified collision check. Validate malformed inputs as 422 before creating side effects. Stale management changes return 409 `stale_revision` with currentRevision; an exact-file replacement returns 412 `content_changed`. No automatic pruning of receipts/candidates/tombstones.

Lists of deliveries, KOReader bindings and KOReader conflicts use page=0,size=50, cap 200, total filtered to the caller's visible resources; stable UUID tiebreak order. No omission from a page means deletion. Credential and recipient lists return active entries only; revoked/deleted evidence is retained privately and returned by the relevant idempotent revoke/delete result. At most 50 active integration credentials per account and 100 active saved recipients; reject creation past the limit with 422 `limit_exceeded`. Revoke is idempotent, keeps metadata, and invalidates all in-flight authorization opportunities before subsequent use. Account disablement and library-grant loss are checked on every wire request and again before queued mail submission.

All three integration services start disabled until an administrator enables them. Integration defaults: 25 MiB raw attachment maximum (26,214,400 bytes), operator-adjustable up to 100 MiB; 10 accepted delivery requests per user per rolling hour, configurable 1-100. Count new delivery intents, not identical API replays, atomically. Enforce a bounded request body (64 KiB management; 32 KiB KOReader), bounded strings, request/connection deadlines and no credentials/progress/book text in logs. Feature flags and limits are application settings, not permission to activate GitHub Actions.

## Credentials

The signed-in UI generates a cryptographically random 32-byte base64url password before POST /integration-credentials and shows it only in the creation flow; API callers supply equivalent entropy. The password is 32-128 base64url characters; length/schema validation is necessary but not an entropy proof. The server returns metadata only, never the supplied password. A stable opaque protocol username is generated separately from the main account username. The UI retains creation material only long enough to complete/replay that explicit request and clears it on success/dismissal/logout; do not persist it in IndexedDB/localStorage or queue generic secret writes.

`kind=opds`: Basic username/password authenticate only /opds/**. `kind=koreader`: one credential per installation; the user enters its generated password in KOReader, which transmits MD5(password) as x-auth-key with x-auth-user. Store the transmitted-key verifier using the existing slow password-verification policy; the MD5 value itself is reusable protocol credential material. Store no cleartext or reversible app-password key. Credential creation receipts contain only returned metadata and safe request fingerprint. Changing the main password does not secretly create a new protocol credential; disabling the account invalidates its use immediately. Revocation is explicit and permanent; create a new credential to replace it.

## OPDS publication identity and routes

Unauthenticated OPDS resources consistently return 401 with a WWW-Authenticate Basic challenge. Mount /opds/v1 (Atom) and /opds/v2 (JSON) at the app/server origin. They are outside /api/v1 and have no reader-origin access. Support root navigation, /publications list/search and /publications/{publicationId} detail in both versions, plus /opds/v1/search.xml OpenSearch. Root links include all publications and granted libraries. List queries: q is a literal NFC-normalized case-insensitive substring over public title/author/series metadata; libraryId and mediaKind restrict results. Sort normalized display title then UUID. Generate absolute same-origin links using the configured public origin, never an untrusted Host/Forwarded value; no secrets in URLs. This hostname-based deployment does not add web path-prefix support.

Use one stable publication UUID for each ebook/comic edition or audio file, consistent across both feed versions and file moves. The UUID is a database/mapping identity, never a hash/path guessed by callers. Current contentVersion and exact source file appear in acquisition URLs. For audio the displayed label includes recording title and one-based file order; description states it is an individual file, not a complete-recording package. Do not expose an audio file absent from an active recording/library relationship. Original-file acquisition does not require that this client can decode/play the format; report those as distinct capabilities, and never advertise unavailable bytes as present.

Every acquisition URL is /opds/files/{fileId}/versions/{contentVersion}/content. Reuse the shared authorization, path containment, original byte serving, MIME, Content-Disposition, size, strong version ETag, HEAD, Range, 206/416 and 412 replacement checks; do not broaden the general bearer endpoint to accept Basic. OPDS wrappers may authenticate then invoke the same service. Credentials and grants are rechecked for every request including range retries. OPDS artwork uses /opds/publications/{publicationId}/artwork GET/HEAD, checks the same grant, serves only the mapped edition/recording's authorized artwork, has private/no-store caching, actual image MIME and no body on HEAD; absent artwork returns 404. Never expose a more-permissive cover URL.

An authenticated local acquisition uses the generic `http://opds-spec.org/acquisition` relation, not open-access. Atom requires standard Atom/OPDS fields/namespaces and appropriate navigation/acquisition media types; OpenSearch advertises the versioned list/search template. JSON feeds use application/opds+json and standalone publications use application/opds-publication+json. Include standard self/start/search/pagination links as appropriate and standard metadata/media-type properties. Escape untrusted XML and JSON; descriptions are plain text, not executable HTML. Feed/metadata responses are private/no-store with Vary: Authorization. Do not add public cache leakage or credential redirects across origins.

The small local JSON envelope schema is NOT full OPDS conformance validation. Implementation acceptance must pin and vendor the official OPDS/Readium schema set with provenance/license/checksums, validate full feeds/publications, and apply semantic link checks plus namespace-aware Atom validation. No runtime schema network fetch. Include at least one actual OPDS client/emulator and independent parser evidence, not just the producer parsing itself.

## SMTP configuration and recipients

Admin configures /admin/delivery/smtp; a user configures /delivery/smtp. /delivery/transports returns availability/revision only for server SMTP, never its username/host/password. Personal reports contain only that user's configuration and `hasPassword`; no password suffix. Config missing returns configured=false with revision zero and harmless display defaults, not 404. Test endpoints compare current configuration revision, connect/authenticate only, return sanitized success/failure and send no message.

SmtpWrite secretAction=replace requires a nonempty password; keep/clear require password=null. keep needs an existing encrypted secret when authentication is configured; clear removes it. A nonempty username requires a configured password; empty username plus no secret means unauthenticated SMTP, allowed only if the operator's selected transport supports it. TLS is required STARTTLS or implicit TLS with hostname/certificate verification; local_test_plain is permitted only with explicit development/test mode and a loopback test sink. Do not offer production certificate-ignore or cleartext downgrade flags.

Use authenticated encryption (for example standard-library AES-256-GCM) with a dedicated operator key ring: active key ID plus 32-byte key; store key ID, nonce and ciphertext, not a derived login/JWT key. Validate unique nonces; wrong/unavailable key is configuration_unavailable (503) and leaves stored data intact. Document backup/key-rotation steps; do not invent background secret recovery. A config change increments its revision and queued requests naming the old revision fail, rather than using another account/endpoint. Administrator-controlled SMTP may use a local operator relay. For personal endpoints, reject nonpublic, loopback, link-local and metadata-address destinations outside explicit local-test mode; resolve/validate every connection address and avoid DNS-rebind bypass. No arbitrary URL or redirects, no connection to other services under a pretended SMTP test.

Recipients belong to the authenticated user. PUT accepts a client UUID at base zero, later updates increment revision. DELETE retains a tombstone and increments revision; identical operation replay is stable. Reject CR/LF and invalid mailbox syntax in addresses/display names/from/filenames/subject fields before constructing MIME. No arbitrary request `to`, BCC or cross-user recipient IDs. SMTP ownership permits user-chosen saved addresses; no email verification campaign or real-person mail is authorized by implementation testing.

## Durable SMTP attempts and visible results

POST /deliveries explicitly names fileId, contentVersion, recipientId plus revision, transport choice plus revision, a new operationId, and normally resendOf=null/acknowledgePossibleDuplicate=false. Recheck granted, available catalog file and attachment limit before enqueuing; include original ebook/comic and individual original audio. Capture recipient/config identity and revisions, not passwords, in the delivery intent. Do not store duplicate book bytes in a public job payload. Atomically create request/receipt/River job. API replay returns the original 202 body even if status later advanced; GET is the current status.

State transitions:

- queued -> sending: worker obtains a durable exclusive attempt lease, revalidates account/grant/current file version/recipient+transport revisions and availability. A second worker must not submit the same attempt.
- Before any DATA terminator could be sent, persist the submission boundary/attempt number. A failure proved to precede that boundary can become retry_wait for transient SMTP 4xx/connection failure, at delays 5 s then 30 s, at most three attempts total. Permanent 5xx or invalid/changed inputs -> failed. Tests inject a controllable clock.
- Final successful SMTP acknowledgement persisted -> accepted. This only means the next server accepted responsibility; never claim inbox delivery.
- Network ambiguity at or after the submission boundary, or recovery of a crashed sending attempt -> outcome_unknown. No automatic resend or transparent River retry may submit another message. The conservative boundary can yield unknown even if no bytes ultimately arrived; honesty and no duplicate retry take precedence.
- Cancellation is permitted only for queued/retry_wait at current revision; cancellation and submission claim race transactionally, one wins. A sending/accepted/unknown/failed request cannot be cancelled as if it had been recalled (409 delivery_not_cancellable).

An explicit resend of failed/unknown/accepted history uses a new operation, `resendOf` pointing to an owned delivery, and `acknowledgePossibleDuplicate=true`; the UI warns for accepted/unknown. Revalidate all current file/recipient/transport inputs; never resurrect or mutate the old result. `resendOf` alone without acknowledgement is 422 duplicate_acknowledgement_required. Rate limiting counts the new request. If source grant is lost, history may retain its own request IDs/timestamps/sanitized outcome but must redact newly inaccessible catalog labels/paths; GET must not leak bytes or another account's history. Raw SMTP text/addresses/passwords stay out of generic logs/errors.

## KOReader wire protocol and lookup

Root /1 routes are a compatibility adapter: GET healthcheck returns {state:OK}; POST users/create always returns 403 code 2005 registration disabled without logging the body. GET users/auth validates x-auth-user and x-auth-key and returns {authorized:OK}. GET syncs/progress/{document} returns an empty object for an authorized exact-version binding with no position, otherwise the bounded upstream progress envelope. PUT syncs/progress takes the upstream document/progress/percentage/device/device_id fields and returns document/timestamp only when that exact outcome is accepted/replayed. timestamp is server Unix seconds for display/compatibility, never conflict ordering. Reject unknown lifecycle methods/routes with 404/405; do not implement account create/password/delete from upstream accidentally.

Wire error envelope is numeric code and bounded message: 2001 unauthorized (401), 2003 invalid fields (400), 2004 invalid/missing digest (400), 2005 registration disabled (403), 2006 document unavailable or unbound (404), 2007 retained candidate (409), 2008 content changed (412), 2009 feature/config unavailable (503). Return no private IDs/paths in these errors. Admin/account/credential gates run before catalog lookup. GET unknown, inaccessible and ambiguous digest use the same 404 envelope (not false empty success); web owner-only binding UI can explain its permitted candidates. A valid file with no source position returns {}. The pinned client may show generic failure for unlisted status codes: validate real failure behavior, not a fabricated successful response. Metadata supplied by newer clients is optional bounded untrusted display data and must never select a file or overwrite catalog metadata.

Digest is 32 lowercase hexadecimal bytes. Binary partial MD5: hash up to 1024 bytes at offset zero, then up to 1024 at offsets 1024*(4**i), i=0..10, stopping at EOF. Use bounded reads and stable-file/content-version checks; include sparse >1 GiB vector evidence in implementation acceptance. These nine preparation vectors come from the archived documented algorithm; independently compare against pinned upstream/client output before claiming compatibility. Filename digests are explicitly unsupported. Recompute/index through a durable bounded job for existing current files and new scan versions; unavailable indexing is an honest not-ready result, never an all-files backfill on an HTTP request.

Lookup joins catalog/grants/account scope before matching. A unique permitted file/version can be selected implicitly; multiple permitted matching editions/files require a per-credential owner binding via /koreader/bindings. A digest collision with inaccessible files must neither disclose them nor accidentally select them. A binding compares revision, exact file/version and credential ownership, and invalidates on replacement; no transfer of saved progress. KOReader /editions/{id}/koreader-position is a separate source report with raw progress/percentage and its own server revision. Do not reinterpret it as a Foliate/PDF/comic locator or alter completion/history/smart-shelf state.

## Conservative KOReader revision adapter

Stock KOReader supplies no base revision or operation ID, so a GET alone cannot prove the causal base of an offline upload. Persist per-owner exact file/version source state, per-device credential baseline, immutable normalized-payload receipts, and private candidates. Device labels/device_id do not authorize or choose winners.

1. A credential must read the bound document before an initial update. For an empty source, that read establishes baseline zero. A read of a nonempty source with no adopted baseline is an observation only; writes require a retained candidate and explicit web resolution. A read never advances an existing stale baseline simply because it returned a newer record.
2. Accept a new payload only when the credential's adopted baseline equals the current source revision, content version still matches and no unresolved candidate blocks that device/document. Atomically update source revision, advance that credential's baseline and save the response receipt. Backward progress is valid under the same rule.
3. Missing/stale baseline or unresolved candidate returns 409 and retains the candidate without changing canonical source state. Changed bytes returns 412; any retained candidate remains attached to the old exact version and cannot be applied to new bytes. Deduplicate repeated payload candidates rather than appending indefinitely.
4. Use an immutable normalized fingerprint over credential/file/version/document/progress/percentage/device fields for wire replay (metadata is not authority). A repeated accepted payload returns its saved success/timestamp without a mutation only while that accepted result is still canonical. If canonical state has since changed, retain a deduplicated candidate and return 409 rather than claim the old place is currently saved. A repeated refused payload returns its recorded failure/candidate without another revision or candidate, even after resolution. Since the wire cannot distinguish retry from an intentional exact return to a previously submitted payload, that exact-return intent may require explicit owner review; document this limitation instead of claiming native operation identity.
5. An authenticated owner resolves a candidate with a new management operation and expected current source revision. keep_server resolves without changing canonical position; use_candidate revalidates bytes/grants and applies the retained position at a new source revision. Keep all payload receipts, so an old retry cannot undo resolution. A concurrent resolve that loses returns 409 with durable evidence. Resolved candidates do not resurrect. For an intentional exact return to a previously rejected/resolved place, POST /koreader/conflicts/{conflictId}/reapply takes a new operation and current source baseRevision, validates owner/grants/current exact bytes and applies that retained place as a new explicit event/revision. It requires a resolved candidate, keeps the old candidate and receipts immutable, and returns 409 on a race. The UI labels this deliberate action separately from an automatic retry. Grant loss or superseded bytes prevents applying a candidate.
6. Resolution permits that credential to establish a new baseline on its next read only if the source revision still equals the explicitly resolved revision; otherwise it is stale again. Preserve the immutable receipt fence. Unmodified client cannot silently rebase queued old writes. The user sees conflict status/actions in Litara; no cross-engine conversion is implied.

Per-device credentials and explicit handoff review add friction but preserve ADR-0015 when a protocol cannot echo revisions. Do not replace this with last-write-wins or a native 409 workaround returning false 200/202. If the pinned client cannot complete the flow, report the reproducible boundary and request a concrete protocol decision; continue independent work. No changed architectural decision is authorized by an inconvenient test.

## Preparation versus completion

Static checks establish schema/example/reference consistency, collision/auth declarations, deterministic digest vectors and complete operation-to-scenario inventory. They cannot establish OPDS conformance, SMTP correctness, cryptographic operation, KOReader interoperability, browser behavior or hardware success. The implementation owner supplies actual parser/client/sink/restart/API/browser results and a clean-commit handoff. T007 retains real devices, broad corpus/codec coverage, NAS/TLS/hardware/Android integration and release/migration gates. Actions stays disabled and no real email is sent during implementation.

## Reproducing preparation checks

Use Python 3 with the existing pinned `scripts/contracts/requirements.txt` packages in a disposable environment. For example on Windows from the repository root:

```powershell
python -m venv .tmp/t006-validator
.tmp/t006-validator/Scripts/python -m pip install -r scripts/contracts/requirements.txt
.tmp/t006-validator/Scripts/python scripts/contracts/check_t006.py
pwsh -NoProfile -File scripts/Validate-Adrs.ps1
```

Use the same environment for check.py/check_t005.py/compare.py. compare.py additionally needs the repository's selected Go toolchain/module dependencies. Dependency caches are not committed source; an exported checkout must supply those dependencies explicitly. The legacy optional `.tmp/t003-validation` path remains supported by the existing checkers; no hidden source files are required.
