# T003 persistence and ownership boundary

This is a minimal seeded integration model under ADR-0006/0013/0018–0022/0024/0030–0043, not T004 ingestion policy. Use PostgreSQL, sqlc/pgx and Goose. Extend the single first-party init migration until production; leave River's independent schema/history untouched. Existing inspection requests are diagnostic records, not the public file identity.

| Logical entity | Required state / invariant |
| --- | --- |
| server_identity | One persisted server UUID; separate from host URL, credentials and database name |
| users | Stable UUID, normalized unique username, display name, password verifier, active/admin flags; no plaintext password |
| libraries / user_library_grants | Stable UUID/name; explicit unique user/library pairs; admin does not bypass read grants |
| sessions / access credentials | User/session UUID, native/web kind, device display name, created/last-used/idle/absolute deadlines, revocation; credential verifiers; transactional refresh generation |
| refresh exchanges | Session + old token verifier/generation + request UUID, protected result only for 60s, nonsecret replay association afterward; never put refresh secrets into generic operation receipts |
| titles | UUID and display title/authors/series data sufficient for seeded recordings; no auto grouping by matching title text |
| recordings | UUID, title/library relation, narrator/display/artwork metadata, layout revision and explicit readiness/issues; one library owns a seeded recording |
| files / content versions | Stable file UUID and separate UUID version, original byte locator kept internal, MIME/size/duration/availability; identity is not the path/hash |
| recording files | Recording/file/version, explicit unique contiguous order; derive totals/whole starts, no fabricated duration |
| chapter sources / effective chapters | Source provenance, raw evidence, protected edits, validation issues; effective anchors use file/version/offset and source/generated distinction |
| position state | Unique user/recording, server revision, nullable file/version/offset/layout anchor, capture/receive time and originating device context |
| per-device position evidence | User/session or device scope and file/version anchor; keep device candidates even when canonical current position advances |
| completion state / title history | Separate user/recording completion revision, current finished flag; append transition evidence/title history; no bulk completion of other recordings |
| operation receipts | Unique user/recording/operation UUID across mutation kinds; normalized request fingerprint, original status/body; created time; no automatic pruning |
| conflicts | User/recording, operation/reason, original candidate event/anchor/base/layout, current-state context, created/resolved metadata; no automatic pruning |

Use foreign keys/unique constraints to prevent duplicate grants, memberships, receipts and canonical states. Authenticated user IDs come from the validated session, never from a mutation body. Administrative writes, grant changes and relevant session revocation must be atomic. Position/completion writes and conflict resolution lock or compare-and-swap their state/receipt rows in one transaction. Never commit a revision without its receipt or a 409/412 receipt without its durable candidate. Capture time must not select the winner.

First admin bootstrap must serialize against another bootstrap attempt. The seed operation must be explicit/local, use synthetic users/passwords and generated media, remain repeatable without duplicate logical fixture data and never run automatically at server startup. Derive actual sizes/durations from generated bytes using the T001 inspector. Keep seed credentials out of arguments and Git. Use deterministic UUIDs in contract JSON only as public test identifiers; production UUID generation stays opaque to clients.

The seed includes two accounts, an administrator with initially no library grant, two libraries with different grants, one title with two distinct recordings, a three-file recording (60/90/30 seconds) with cross-file chapter navigation, one chapterless ready recording, an incomplete/missing-file case, generated thumbnail/cover and fixtures for content replacement/order change. JSON fixture sizes are abstract schema examples, not binary hashes or an excuse to stub actual media tests. Generate media at test time; do not commit book/media binaries.

## Ownership

T003 initially owns the minimal accounts/grants/session and title/recording/file schema, API contract, seeded data and Android adaptation. T004 must start from integrated T003 and extend this model for actual discovery/move/version matching/grouping/import/NAS reconciliation. T003 does not invent those algorithms. Path-keyed T001 diagnostics may be retained, but public file IDs and versions must be separate and consistent everywhere.

T004 consumes T003's identities, ordering, content/layout revisions, readiness and normalized chapter source rules. T004 may not overwrite user edits or reinterpret an existing file ID as a path. Any necessary new ingestion choices go through ADR acceptance before implementation. No concurrent T003/T004 writes to server, init, shared contract or seed paths without explicit narrowed scopes.

Android is AGPL; Go/contracts are first-party MIT. Do not copy imported Android reader/player implementations into the MIT server/contracts. Shared JSON contract fixtures are newly authored protocol data, not extracted AGPL implementation source.
