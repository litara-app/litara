## Decisions and interpretations to review

1. Audio sort order: "normalized display title then UUID" is implemented as normalized base title, then recording, then file order, then UUID, so file 10 does not sort before file 2.
2. Original downloads use `catalog.ResolveOriginal` (skips only the playback-readiness gate), so an incomplete recording's available file is downloadable, per ADR-0073's "distinct capabilities". Unavailable/size-unknown files are never advertised.
3. Ungranted, unknown, tombstoned and incomplete protocol objects all return the same 404 on OPDS.
4. OPDS requires HTTPS (TLS or `X-Forwarded-Proto: https`, the existing requestOrigin rule) unless `DevInsecureHTTP`; plain HTTP gets 403 `https_required`. The KOReader surface is not HTTPS-gated (the contract restricts Basic over HTTPS for OPDS only).
5. Empty OPDS 2.0 result pages include a `navigation` link to the root because the official schema forbids an empty `publications` array and requires one of publications/navigation/groups.
6. Receipts reuse `t005_receipts` so an operation UUID cannot collide across T003/T005/T006.
7. A refusal on the KOReader wire commits its candidate and receipt (it is not rolled back). An unresolved candidate blocks that device until the owner resolves it, including after the device re-reads.
8. Protocol 429 uses KOReader code 2010 (the contract only fixes 2001-2009).
9. Public origin comes from `LITARA_PUBLIC_ORIGIN`; OPDS returns 503 `configuration_unavailable` without it. Note this is currently validated only when the web app is served.

10. Created recipients and bindings start at revision 1 (T005 convention: base 0 means "does not exist"), so two concurrent creates cannot both succeed.
11. SMTP submission boundary: persisted after the server accepts the DATA command and before any message byte. A definite 4xx/5xx reply after the terminator is `failed` (known not accepted, not retried automatically); anything else after the boundary is `outcome_unknown`. Pre-boundary 4xx/connection errors retry at 5 s then 30 s, at most three attempts; TLS verification, authentication and 5xx failures are permanent.
12. A `sending` attempt holds a lease (send timeout plus 30 s). A redelivered job during the lease re-schedules itself; only an expired lease is recovered as `outcome_unknown`.
13. Personal transports may not target loopback, private, link-local (including 169.254.169.254), CGNAT, multicast or unspecified addresses. Every connection resolves the name, requires every answer to be public, and dials one of those exact IPs (rebinding-safe). Loopback is allowed to a personal transport only with `LITARA_SMTP_ALLOW_LOCAL_TEST=1`. The administrator's server transport is unrestricted (local relay).
14. Operator configuration: `LITARA_SMTP_KEYS` (`id:base64key,...`, 32-byte keys), `LITARA_SMTP_ACTIVE_KEY`, `LITARA_SMTP_ALLOW_LOCAL_TEST`. There is no key-rotation tool or background re-encryption: to rotate, add the new key, set it active, re-save each stored password, then retire the old key. Back up keys with the database; without the key the passwords are unrecoverable by design.

## Known limits (honest)

- Atom (OPDS 1.2) has no official machine schema in the pinned set and was not RELAX NG validated.
- The pinned JSON-schema library's built-in `uri-template` check rejects the RFC 6570 `{?query}` operator (even the spec's own example); the test registers its own RFC 6570 grammar for that one format.
- Digest agreement: KOReader's own `util.partialMD5` produced the same digest as the server for the test EPUB in the real-client run; sparse >1 GiB agreement with KOReader is still only the independent re-implementation and contract vectors.
- **Real-client findings (decisions needed):** (a) OPDS 2.0 search: the template is `{?q,libraryId,mediaKind}` but KOReader appends `?query=`, so 2.0 search silently returned everything. **Fixed at your request** by accepting `query` as an alias for `q` on both feeds (`internal/httpapi/opds.go`, `TestOPDSSearchQueryAlias`; `q` wins). The contract in `contracts/t006/` is unchanged and still names only `q`; **the coordinator should ratify the alias or amend the contract.** (b) KOReader shows only a generic failure on the 409 retained-candidate response (its API spec does not list 409), so the person must learn about the conflict in the web settings. The contract anticipated this; a protocol decision is only needed if that is not acceptable. (c) The real client sends HEAD before every OPDS GET; the server answers it.
- The real-client runs exercise KOReader's client code under LuaJIT with two inert stand-ins (UIManager/Device for sync; widget classes for OPDS). They do not run the KOReader application, its UI, a device, or real TLS (a forwarding proxy stands in for TLS termination).
- Digest indexing sweep picks random unindexed files; a permanently unreadable file stays unindexed (honest not-ready) and is retried.
- Credential verification is cached in memory (10 min, keyed to the exact verifier) to avoid an argon2 hash per request; revocation and account state are still read from the database on every request.
- Restart behavior for KOReader state rests on all state being in PostgreSQL; there is no process-restart test yet.
- The SMTP crash scenario is a test hook that abandons the attempt after the durable boundary, not a killed process; the key-loss scenario swaps the in-memory ring rather than restarting with a different environment.
- The new browser spec runs once, in Chromium (it changes shared server state). The other browsers ran the existing suite only. Accessibility is automated (axe, desktop and phone widths) with no manual screen-reader pass.
- The "server address" shown beside a new KOReader credential is `<origin>/1`, derived from the contract's root mount. It has not been checked against a real KOReader client.
- The web UI cannot show a file's KOReader fingerprint (the contract does not expose it), so binding a document means typing the 32-character fingerprint on the edition page.
- Delivery history rows show the recipient, time, transport and state only: the delivery wire body carries file IDs, not file names, so the history cannot say which book was sent. Showing it needs a contract addition (coordinator decision).
- Resend and reapply use a single deliberate button or dialog; resend requires an acknowledgement checkbox, reapply has explanatory text but no second confirmation.
- SMTP AUTH is PLAIN only (over verified TLS or the explicit loopback test mode). No LOGIN/CRAM-MD5/XOAUTH2.
- Acceptance used a local loopback sink only. No real SMTP server, provider or mailbox was contacted, and nothing here shows inbox delivery.
- Delivery history rows keep the recipient name/address snapshot for the owner; there is no redaction pass for catalog labels because the wire body carries none.

## Web behavior to review

- A credential password is generated in the browser (`crypto.getRandomValues`, 32 bytes, base64url), sent once, shown once, and lives only in the page's React state; dismissal, leaving the page or signing out discards it. Nothing is written to local/session storage or IndexedDB (asserted in unit and browser tests). Sign-out already drops every cached query.
- Stored SMTP passwords are never returned or displayed; the field is write-only and the form derives keep/replace/clear from what the person typed.
- Sending requires an explicitly chosen recipient and transport (nothing preselected, unavailable transports disabled, no fallback). An identical retry after a failed request reuses its operation ID so the server returns the same delivery; a new intent gets a new one. Status wording is "Accepted by the mail server", never "delivered".
- All writes use the existing cookie + CSRF client. None of these writes go through the offline pending queue, so secrets and sends are never queued or replayed after sign-out.
- KOReader positions are shown as a separate, labelled source with the saved progress string rendered as plain text.
