### Review pass 2026-11-16 (the two blockers, the WebKit issue, stale text)
- **Stale account responses (fixed).** A request issued under one account could resolve after another account signed in and then be applied to that account's cache or UI. `api/client.ts` now keeps a session epoch that advances on sign-in, sign-out and expiry; `api()` (and the raw comic-page and book-range fetches) throw `StaleSessionError` when the epoch changed while the request was in flight, so such a response is never delivered. `auth/session.tsx` advances the epoch before dropping cached data, cancels every non-session query, and cancels an in-flight session read before writing the new session. A queued write in flight at the switch gets a non-`ApiError` failure, which the pending queue already treats as a transient network failure: it is retried with the same operation ID and base revision (or held when a different account is signed in), so nothing is lost or applied twice. Tests: `src/api/client.test.ts` (a response that arrives after the epoch advanced is discarded; a request made afterwards is delivered). Not covered by a browser test: a slow response racing a real sign-in.
- **7z allocation limits (fixed).** The earlier pre-check bounded only the claimed file count. `bodgit/sevenzip` also allocates per folder and per pack stream before validating, and a folder costs about three header bytes, so a header of at most 16 MiB could still claim millions of folders. `sevenz_precheck.go` now refuses, as a typed limit error and before the library sees the archive, a header that claims more folders or pack streams than the configured entry ceiling, or more than four coders per permitted entry in total (applies to plain and LZMA-encoded headers). Tests: `TestSevenZipFolderAndStreamClaimsAreBoundedBeforeAllocation` (a few MB file claiming 10,001 and 2,000,000 folders) and `TestSevenZipFolderCeilingFollowsConfiguredEntryLimit`, with `archivetest.WriteSevenZipFolderBomb`. Still unmeasured: peak memory and time on large real archives, and decoding of 7z deflate/bzip2/delta/BCJ with hostile input.
- **WebKit navigation issue (fixed in the tests).** In WebKit `reader.spec.ts` `openBook` failed (90 s timeout waiting for the "Read" link): after the search box was filled, the helper clicked the title text and then `getByText(/EPUB/)` before the page had navigated, and the second click hit the still-visible "Corpus EPUB" card, landing on the wrong title. The product was not at fault. `e2e/support.ts` now provides `openTitle` (waits for the matching card, for the other cards to disappear and for the title URL and heading) and `openEpubEdition` (waits for the edition URL); `reader.spec.ts`, `offline.spec.ts` and `admin.spec.ts` use it. The same defect pattern existed in all three.
- **Stale handoff text (replaced).** The old "Final review" block listed items that had since been closed and carried counts from an earlier run.

- Routes: `planRecordingRepair` (201), `getRecordingRepair`, `approveRecordingRepair`, `executeRecordingRepair`, `cancelRecordingRepair`. Administrator AND a grant on the library; plan create is replayable by operation ID; approve/execute/cancel compare the plan revision (409 `stale_revision`) and the plan state (409 `plan_state`). Execute locks the plan then the source recordings in UUID order, revalidates layout revision, file set and versions (approval never waives this), and either applies everything or nothing. A source that changed, or was already repaired, returns 412 (`layout_changed`, `content_changed`, `recording_repaired`) and marks the plan `stale`.
- Validation: merge needs at least two sources and one output; split one source and at least two outputs; sources must be active, in one library and one title, with distinct file sets; outputs must be an exact one-to-one partition of the sources' current file/version memberships with unique keys and explicit order. File IDs, content versions and bytes are never touched.
- Apply: successors get new UUIDs, the sources' files in the planned order, narrators merged from the sources that supplied files, artwork from the first source, and chapter evidence (including protected user edits) filtered to files they hold. Sources become tombstones (`recordings.tombstoned_at`, ordered `successor_ids`); all catalog, count, scan, shelf and authorization queries read the `active_recordings` view, so a tombstone cannot be listed, served, matched by a rescan or counted. Successors start unfinished with no canonical position. Each account that has a grant receives its own source position as an explicit unresolved candidate (existing recording-position conflict model, reason `repair_source`) only where the anchored file/version belongs to that successor; resolving it uses the normal revisioned protocol. Source completion, history, positions and conflicts are retained and readable; nothing is copied or auto-selected.
- Old clients: snapshot and artwork of a tombstone return 409 `recording_repaired`; old position and completion writes return 412 `recording_repaired` with a durable candidate (`conflictId`) and `successorRecordingIds`, shown only to callers who passed the grant check (a user whose grant is revoked gets a plain 403).
- Verified (real PostgreSQL): admin/grant authority; 10 invalid-plan shapes; stale layout 412; plan replay; approve/execute ordering and stale revisions; execute replay returns identical successor IDs; second execute and cancel-after-apply refused; listings hide tombstones and show successors; per-user candidates with the successor's layout revision and no source completion carried over; candidate resolution; old snapshot 409, old position/completion 412 with retained candidates; source state and history still readable; an unrelated recording untouched; hint hidden after grant revocation; two competing split plans (second 412 and marked stale); cancel. Full server suite, vet, sqlc diff, parity and the 15 real-stack browser tests still pass.
- Not done: no web UI for repair; chapter rederivation copies evidence but does not re-run chapter selection checks beyond reusing the existing selector at read time; narrators/protected metadata edits on source recordings are not copied to successors; position evidence per device is not turned into candidates (only each account's canonical source position); the contract text asks to update the T003 contract and fixtures with the additive `successorRecordingIds` error field, but `contracts/t003` is outside this task's write scope, so that edit is left to the coordinator (T003 `Problem` is already open to extra properties, and parity passes); tombstone cleanup and any un-repair are intentionally absent.

## Milestone 9 (partial): durable pending-write queue and conflict recovery (web)
- Governing ADR: 0068 (online web with recoverable pending writes), plus 0065/0066 revision and conflict rules.
- `apps/web/src/pending`: an IndexedDB store (memory fallback with an explicit warning) of writes scoped to server origin + account; a queue that stores each write before sending, keeps the original operation ID, base revision and content version across retries, sends per resource in order, backs off on network/5xx/429, **pauses on 401** (the app locks to the sign-in screen and keeps every record), **marks a 403 as blocked** (access removed) instead of dropping it, **keeps a 409/412 as a conflict** with the server's problem body, and never prunes automatically. Before each send the sender confirms the browser session still belongs to the record's owner, so one account's queue is never sent as another. Records of other accounts are never loaded, shown or sent; same-account sign-in restores them.
- Wired through the queue: **annotations** (create, edit note, delete; the reader shows unsent items as "not saved yet", failures as "needs attention", and a banner when the server is unreachable) and **reading positions** (latest-wins coalescing only for a write that was never attempted; a possibly-applied write is chained to the next base revision). The existing position conflict banner still works and now also clears the queued write.
- Pending page (`/pending`, header badge): waiting vs needs-attention lists, try again, discard (explicit confirmation), and conflict resolution through the server's `/personal-conflicts/{id}/resolve` ("Keep what is saved" / "Use my change"), after which later queued writes to that resource are dropped because they were based on it.
- Verified: 13 vitest tests (queue ordering, chaining, coalescing, retry with identical body, conflict halting only its resource, 403/401 behavior, account scoping and reload restore over fake-indexeddb) and 4 real-stack browser scenarios in Chromium, Firefox and WebKit (12 runs; 32 total with reader and administration): a write made while the API is blocked survives a reload and is delivered afterwards; a response lost after the server applied the write is retried with the same operation and yields exactly one annotation at revision 1; pending data is locked at sign-out, not sent when a different account signs in, and delivered when the owner returns; a queued edit that conflicts with a change from another device is kept and resolved on the pending page. The browser run also found that `/pending` was missing from the Go SPA route list (fixed in `webui`).
- Not done / limits: shelves, completion and administrator writes still go straight to the server and show an error when the server is unreachable (they are not queued); there is no offline reading or service worker, by design; sending relies on page activity (timers, the `online` event, tab visibility), not a background worker, so a closed tab sends nothing until the account is next open; `navigator.onLine` is not trusted, only failed requests; conflict resolution for a queued position is only via the reader banner or the pending page, not a dedicated side-by-side view; no test of storage quota exhaustion or private-mode IndexedDB failure beyond the memory fallback; no revocation test that removes a grant mid-queue end to end (the 403 path is unit-tested); keyboard and screen-reader review of the pending page not done.
