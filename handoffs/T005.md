## Milestone 7 (partial): reviewed recording repair (server)
- Governing ADR: 0070. All 38 contract operations are now implemented and `compare.py` parity is OK with zero pending.
- Routes: `planRecordingRepair` (201), `getRecordingRepair`, `approveRecordingRepair`, `executeRecordingRepair`, `cancelRecordingRepair`. Administrator AND a grant on the library; plan create is replayable by operation ID; approve/execute/cancel compare the plan revision (409 `stale_revision`) and the plan state (409 `plan_state`). Execute locks the plan then the source recordings in UUID order, revalidates layout revision, file set and versions (approval never waives this), and either applies everything or nothing. A source that changed, or was already repaired, returns 412 (`layout_changed`, `content_changed`, `recording_repaired`) and marks the plan `stale`.
- Validation: merge needs at least two sources and one output; split one source and at least two outputs; sources must be active, in one library and one title, with distinct file sets; outputs must be an exact one-to-one partition of the sources' current file/version memberships with unique keys and explicit order. File IDs, content versions and bytes are never touched.
- Apply: successors get new UUIDs, the sources' files in the planned order, narrators merged from the sources that supplied files, artwork from the first source, and chapter evidence (including protected user edits) filtered to files they hold. Sources become tombstones (`recordings.tombstoned_at`, ordered `successor_ids`); all catalog, count, scan, shelf and authorization queries read the `active_recordings` view, so a tombstone cannot be listed, served, matched by a rescan or counted. Successors start unfinished with no canonical position. Each account that has a grant receives its own source position as an explicit unresolved candidate (existing recording-position conflict model, reason `repair_source`) only where the anchored file/version belongs to that successor; resolving it uses the normal revisioned protocol. Source completion, history, positions and conflicts are retained and readable; nothing is copied or auto-selected.
- Old clients: snapshot and artwork of a tombstone return 409 `recording_repaired`; old position and completion writes return 412 `recording_repaired` with a durable candidate (`conflictId`) and `successorRecordingIds`, shown only to callers who passed the grant check (a user whose grant is revoked gets a plain 403).

## Milestone 9 (partial): durable pending-write queue and conflict recovery (web)
- Governing ADR: 0068 (online web with recoverable pending writes), plus 0065/0066 revision and conflict rules.
- `apps/web/src/pending`: an IndexedDB store (memory fallback with an explicit warning) of writes scoped to server origin + account; a queue that stores each write before sending, keeps the original operation ID, base revision and content version across retries, sends per resource in order, backs off on network/5xx/429, **pauses on 401** (the app locks to the sign-in screen and keeps every record), **marks a 403 as blocked** (access removed) instead of dropping it, **keeps a 409/412 as a conflict** with the server's problem body, and never prunes automatically. Before each send the sender confirms the browser session still belongs to the record's owner, so one account's queue is never sent as another. Records of other accounts are never loaded, shown or sent; same-account sign-in restores them.
- Wired through the queue: **annotations** (create, edit note, delete; the reader shows unsent items as "not saved yet", failures as "needs attention", and a banner when the server is unreachable) and **reading positions** (latest-wins coalescing only for a write that was never attempted; a possibly-applied write is chained to the next base revision). The existing position conflict banner still works and now also clears the queued write.
- Pending page (`/pending`, header badge): waiting vs needs-attention lists, try again, discard (explicit confirmation), and conflict resolution through the server's `/personal-conflicts/{id}/resolve` ("Keep what is saved" / "Use my change"), after which later queued writes to that resource are dropped because they were based on it.
