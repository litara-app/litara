## Android Litara flow (added in the follow-up "wire it in" pass)

New package `com.litara.feature.litara`, bound through Hilt (`@Singleton LitaraRepository`, `LitaraSessionStore`,
`@HiltViewModel LitaraViewModel`, `@AndroidEntryPoint LitaraActivity`; manifest entry, not exported):

- **Sign-in**: server URL, explicit development opt-in for plain HTTP (refused otherwise), discovery check
  (`product=Litara`, `v1`), native login. Tokens, the pending refresh request id and the identity live in
  `SecureStorage` (device-encrypted). Logout locks the account scope immediately and keeps its data.
- **Library**: authorized list with an offline cached list when the server is unreachable.
- **Detail**: snapshot, chapters (tap to seek across files), incomplete/locked/offline/"update available" states,
  explicit download (staged beside old bytes, published atomically only when every file validates, old bytes removed
  only afterwards), manual finish/unfinish.
- **Playback**: Media3 `ExoPlayer` over the ordered files, from downloaded files when present, otherwise streamed with
  a bearer token and single refresh-then-retry on 401 (ranged requests included). Position is reported every 10 s,
  on pause and on seek through `ProgressSync` (revision-aware, serialized, one pending write kept across restarts
  with the same operation id). Resume asks which position to use when unresolved conflicts exist. Natural end is
  sent only when playback reaches the final file's end (a seek that lands at the end never finishes).
- **Isolation**: every offline artifact is under `OfflineStore/<hash(serverId,userId)>`; tasks are bound to a
  `ScopeToken` and cannot publish after logout or an account switch.

Bugs found by running it for real and fixed: concurrent position reports raced into self-conflicts (now serialized by a
mutex), response bodies were read on the main thread (`NetworkOnMainThreadException`; now read on `Dispatchers.IO`),
and the existing `NoHardcodedUiTextTest` guard forced all new UI text into string resources.

## Auto and Cast on Litara (follow-up pass: "move Auto and Cast over")

Approach: instead of rewriting the imported player around UUIDs (Room keys, `book/<id>` media ids and ~335 tests
depend on Int ids), a `LitaraSource` seam (`feature/player/LitaraSource.kt`) exposes each Litara recording and file as
a **local Int handle** (>= 1,000,000,000; BookOrbit ids never reach it). Handles are allocated once per
server+account scope, persisted in `idmap.json` inside that account's directory, never reused and never sent over the
wire. Everything on the wire, in downloads and in conflicts stays UUID + content version + millisecond offset.

What now works for Litara recordings with the **unchanged** imported code:

- **Android Auto browse/search/play**: the real `MediaLibrarySession` lists them under Library > Titles, finds them by
  search, and plays a tapped book (bearer-authenticated ranged streaming with one refresh-then-retry on 401, or the
  downloaded files). Chapters come from the effective chapter source; a chapter that spans files seeks across them.
- **Progress**: `AudioProgressRepository` writes locally then pushes through `ProgressSync` (revision-aware, serialized,
  offline queue with the same operation id). Resume follows the **server's canonical position, not a device clock**;
  a car never picks a conflict winner (unresolved conflicts stay for the phone's Litara screen to ask about).
  Natural end is sent only when playback reaches the final file's end (a seek landing there never finishes).
- **Cast**: the phone's proxy fetches upstream with the Litara bearer (Litara host only); the receiver URL contains no
  credential and a receiver without the bearer gets 401 from the server directly.
- **Isolation**: a Litara-only account gets its own Room database and download scope (`SessionManager.dataScope`;
  unidentified legacy data is never claimed); caches and the Auto artwork scope include the Litara
  identity. A different account/scope restarts the process once (existing behavior for scope changes), relaunching the
  Litara screen.

Changed/added: `feature/player/{LitaraSource,PlayerRepository,AudioProgressRepository,AutoLibraryRepository,AutoCatalog,
AutoArtwork,PlayerManager,MediaLibraryCallback}.kt`, `feature/litara/{LitaraBackend,LitaraBindings,LitaraRepository,
LitaraSessionStore}.kt`, `core/auth/{SessionManager,DataScope}.kt`, `core/di/{PlayerModule,CastModule}.kt`,
`core/data/ProcessRestarter.kt`. New constructor parameters default to `LitaraSource.None`, so existing hand-built test
fixtures are unchanged.

## Conflict resolution UI

Both flows live in one shared host (`ConflictPromptHost`) used by the Litara shell and the older Litara screen; the
dialog cannot be dismissed without an answer, and nothing is chosen automatically (ADR-0036).

- **Resume conflict, explicit position.** "Choose a position…" lists the recording's files; the user picks a file and
  whole seconds, validated against that file's length before sending. The client sends `use_explicit` with that file id,
  content version and offset (`ProgressSync.resolve`); a fresh device then resumes from it. Keep-server and use-the-other
  are unchanged.
- **Completion conflict.** Completion conflicts arrive in the same unresolved list (`LConflict.completionCandidate`).
  The dialog shows the server state and the kept event and offers keep-server, apply-the-kept-event, or an explicit
  "Mark finished" / "Mark not finished" (`CompletionSync.resolve`, `POST .../completion-conflicts/{id}/resolve`). It
  delivers any queued completion events first and uses the server's current completion revision as the base, so it is
  online-only and never resolves against a stale base. A finish the server preserved (409/412) opens this dialog straight
  away instead of only reporting an error. Before this change a completion conflict would have been answered through the
  position endpoint, which does not accept it.
- Evidence: `ConflictResolutionE2ETest` (real server: explicit position, and keep_server / use_candidate / use_explicit
  completion choices, a double resolve refused), `CompletionSyncTest` (queued events go first, current revision as
  base), and `LitaraConflictUiTest` (emulator, real launcher activity: pick file 3 at 20 s, then explicit "Mark
  finished", server state checked afterwards).
- Final emulator suite: **24 tests per flavor, 0 failures/errors/skips**. The Auto resumption assertion was stale:

  fixture ids stay below the reserved Litara handle range. See "Final PR verification" for before/after evidence.
- Not covered: an explicit natural-end completion with a final position (the UI offers manual events only), a conflict
  whose layout changed while the dialog was open (the server returns 412 and the dialog stays), and the
