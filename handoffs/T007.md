## Findings and decisions needed

**F1 (RESOLVED for EPUB, FB2 and PDF at page granularity in slice 5; still open for KEPUB, MOBI, AZW, AZW3 and sub-page PDF coordinates; original text follows): the server stamps every foliate-family locator with the web engine profile.** `apps/server/internal/catalog/editions.go` `engineFor(format)` derives `engineProfile` from the file format only; the position write (`T005PositionWrite`) has no profile field and the server validates just kind/format. So any native CFI sent today would be stored and later served to the web reader as `ProfileFoliate`. The preserved Android Foliate is a modified, partly older foliate-js (`apps/android/THIRD_PARTY_NOTICES.md`), and `contracts/t005/README.md` says ancestry is not compatibility evidence. Therefore `LitaraRepository.nativeCompatibleProfiles` is empty: positions are stored on-device per file/version only and never sent, and a server CFI is never applied by native. Proposed decision for the coordinator/user (no ADR written): either (a) prove native<->web CFI round trips on the same file/version with both real renderers (layout/font changes, EPUB/FB2/MOBI/AZW3) and add the proven profile to the client allowlist, or (b) add an explicit renderer-profile dimension to the position contract so native positions are stored and compared as a distinct profile. Other work continues; nothing was relabeled.
**F2: Windows checkouts.** See server finding 2 above; a root `.gitattributes` is needed.
**F3: emulator choice.** The user permitted `Pixel_9_Pro` (`emulator-5554`, Android 17) on 2026-11-17 and said it holds nothing important; instrumentation `connectedAndroidTest` would uninstall `com.litara.debug` there.
